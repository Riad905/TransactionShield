# Dataset decision record

- **Status:** recommended, awaiting acquisition approval and exact-file validation
- **Decision date:** 5 September 2026
- **Recommended primary data:** MoMTSim paper-defined dataset version 1, to be identified within Mendeley Data repository Version 2

## Version terminology

Two independent version schemes are involved:

- **Paper dataset version:** the 2025 *Data in Brief* paper ([DOI `10.1016/j.dib.2025.111534`](https://doi.org/10.1016/j.dib.2025.111534)) defines “dataset version 1” as its smaller experimental dataset and “dataset version 2” as a separate, larger generated dataset.
- **Repository release version:** the current Mendeley Data record is repository **Version 2** ([DOI `10.17632/zhj366m53p.2`](https://doi.org/10.17632/zhj366m53p.2)). This number identifies a revision of the repository record; it does not identify which paper-defined dataset variant a particular file contains.

TransactionShield targets the **paper-defined dataset version 1** while using the current **Mendeley repository Version 2** as the authoritative acquisition record. Stage 2 must identify and validate the exact file rather than infer its contents from either version number.

## Decision method

Facts below come from the original data article, dataset record, simulator publication/repository, and official competition pages. Statements about portfolio suitability are engineering judgements. No dataset was downloaded, so paper-reported counts, percentages, and schemas are not yet verified against an exact repository file.

## Recommendation

Use the **paper-defined MoMTSim dataset version 1**, acquired from the current **Mendeley repository Version 2** record, as TransactionShield's primary dataset.

It offers the best overall fit because it combines credible and recent documentation, explicit open licensing, a laptop-manageable size, time order, participant identifiers, interpretable transaction fields, multiple fraud behaviours, and a natural path from SQL feature engineering to event scoring and later graph work. It is also less overused than PaySim, improving portfolio differentiation.

The paper's dataset version 1 is preferred over the paper's dataset version 2 for the first build. The article reports 52.84% fraud for its dataset version 2 and 10.20% for its dataset version 1; on the publication evidence, dataset version 1 is smaller and preserves a meaningful minority-class problem. The 10.20% value remains a **paper-reported expectation**, not a verified characteristic of the exact file TransactionShield will use. Stage 2 must calculate it independently before it appears as an observed project result. Even if confirmed, it is not representative evidence for a real provider.

### Why not the alternatives?

- **PaySim** is the best fallback and a useful later robustness dataset. Its rare fraud rate creates a realistic evaluation challenge and its entity links are valuable, but it is older, substantially larger, extensively used in portfolio projects, and its dataset-specific redistribution terms need confirmation.
- **IEEE-CIS** provides real transactions and much richer features, but access/redistribution restrictions, anonymised features, uncertain online availability, and lack of a clear payer-payee graph make it a weaker foundation for a public, explainable product. It is better suited to a competition-modelling study than this project's main narrative.

## Risks and controls

1. **Synthetic-to-real gap:** describe results only as performance on MoMTSim; do not imply bank or deployment validity.
2. **Label mechanism shortcuts:** inspect fraud rates by type/entity/time, perform feature ablations, and document suspiciously predictive fields.
3. **Post-event leakage:** maintain a feature-availability register; exclude post-transaction balances from pre-decision models unless the intended decision moment makes them valid.
4. **Repeated-entity leakage:** use temporal validation and consider grouping/embargo checks rather than a random split.
5. **Moderate class imbalance:** use PR-AUC and operating-point metrics; do not present accuracy alone.
6. **Dataset/version ambiguity:** record both version schemes and independently calculate row count, fraud count, legitimate count, fraud percentage, schema, file size, and checksum immediately after acquisition is approved.
